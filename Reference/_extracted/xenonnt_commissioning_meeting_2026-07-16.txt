"SCADA1 is dead, long live SCADA1."
The migration of SCADA1 to the new server was completed successfully by Zhaowei and
Mahmoud, with help from Ekaterina and the shifters for the network mapping, testing, and ﬁnal
rewiring.
SCADA2 maintained the operational services  during the work, so alarms, screens, and the
Historian continued running, apart from a few brief planned SCADA restarts.
The only missing functionality while running on SCADA2 was the calibration-sequence
script. This should already have been ﬁxed, but has not yet been tested.
The migration was performed cold: SCADA1 was powered oﬀ, exported with OVF Tool as an
OVA/OVF package, and imported into the new ESXi environment.
Important milestone:  This validates the new hardware, the new virtualization environment,
and our existing SCADA image. It was also the ﬁrst time we performed this type of migration
ourselves, so we now have a tested procedure and know how to repeat it. We can therefore
proceed with purchasing a similar server as the next standby host.
For more information: SCADA1 Hardware Failure and Server Migration - July 2026

HV communication incident - resolved
The HV communication problem appeared spontaneously. It was not preceded by any change to
the SC hardware, software, servers, network, or infrastructure.
At the peak of the incident, 3 out of 4 SY4527 crates could not be accessed through
GECO , and SCADA control was also aﬀected. Direct laptop tests reproduced the same failures
while bypassing the SC network, showing that this was not caused by SCADA or the network
infrastructure.
On July 7, we had a productive Zoom call with CAEN. With their help, the crate ﬁrmware and
HiVoCS software were upgraded, restoring direct communication through GECO.
After the ﬁrmware upgrade, a second problem appeared: the existing OPC DA service could
connect to all four crates at the network level, but it hung during initialization and did not start.
This left SCADA without HV communication.
On July 14, Andrew found the registry location where the OPC server retained its crate
conﬁguration. Clearing and rebuilding this conﬁguration allowed the OPC DA service to start,
and shortly afterward all HV communication returned.
Important distinction:  the original crate communication failure happened before the ﬁrmware
upgrade and remains unexplained. The later OPC problem was a separate
installation/conﬁguration issue with the OPC DA service provided during the troubleshooting.
In the future, we can move to OPC-UA, but this should be done as a planned and fully tested
migration. We already had our own basic OPC-UA backup tested and available as a standby. The
new OPC-UA server provided by CAEN during this incident was not tested, and its compatibility
with Windows Server 2012 R2 is still unclear.
For more information:
https://xe1t-wiki.lngs.infn.it/doku.php?id=xenon:xenonnt:slowcontrol:hagar:HVcrate_july_2026

Accumulator control
We received the technical details from Guillaume. The requested change has two parts:
Filtering of the level signal used for valve control , so the valve does not react to short
ﬂuctuations and noise.
Adaptive pulsing of FV111 , where the valve opening time changes according to the
measured level and system response.
My suggestion is to start with the ﬁlter. It is the simpler and lower-risk part, and we should be able to
implement it in the very near future. Once it is working and the ﬁltered signal is understood, we can
move to the adaptive pulsing.
Some follow-up questions were sent to Guillaume regarding the exact control logic, limits, timing,
safety behavior, and required screens.
At this stage, the change should not require stopping the PAC project. It will only require uploading
the changes to the PAC and updating the EGD conﬁguration on both the PAC and SCADA sides.
We also need a clear installation and testing plan. The main challenge is testing while the detector is
running. We need to deﬁne what SC can test independently, what can be tested during installation,
and what can only be tested during operation.
