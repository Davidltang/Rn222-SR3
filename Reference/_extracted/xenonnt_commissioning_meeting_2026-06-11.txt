Slow Control (Mahmoud)
AEX_To_SMS Update
Why Should You Listen: Our slow control is only as good as our alarm notiﬁcation system. This
code is critical for operation, so I ask for your attention, review, and cooperation.
What Is AEX_To_SMS : AEX_To_SMS  is the notiﬁcation service that receives alarm messages directly
from the XENON SCADA Alarm & Event Express system, records them, and forwards important alarms
by email, SMS, and now Slack. It was written by Miguel Silva.

XENON1TWiki - https://xe1t-wiki.lngs.infn.it/What Changed:
Alarm ﬂood control  was added for email, SMS, and Slack notiﬁcations. More details below.
Slack is now sent directly by AEX_To_SMS , instead of through the old Google Apps Script
that scanned Gmail. This should reduce delay signiﬁcantly. Due to TLS/certiﬁcate limitations on
the SCADA machine, Slack is not sent directly from AEX_To_SMS  to Slack; delivery is routed
through a small remote VM relay, but the delay is still expected to be much shorter than the old
Gmail polling method.
A separate uncensored Slack channel  was added for broad alarm visibility. It receives
alarms with severity > 100 , except SCT099  heartbeat alarms.
The usual Slack channel remains ﬁltered  and keeps the previous formatted messages.
Test commands  were added for database, Slack, uncensored Slack, SMS, LNGS SMTP, Gmail,
and Postmark. They allow testing parts of the alarm-notiﬁcation chain independently, which
makes debugging safer and faster before touching the full running service or disturbing SCADA
operation.
Secrets moved to a local secrets ﬁle  and are no longer kept in code. This allows the code
to be kept in git without exposing passwords, tokens, or webhook URLs.
Why Alarm ﬂood control:  Alarm ﬂoods can happen when a value crosses a threshold repeatedly,
many related alarms arrive together, SCADA restarts, or Alarm & Event Express reports alarm-status
changes. Floods cause SMS cost, mail-server load, nuisance notiﬁcations, and can hide important
alarms inside repeated messages.
Flood Mechanism:  Each unique alarm is identiﬁed by the notiﬁcation channel, alarm code, and
alarm text after removing only measured numeric values. The ﬁrst alarm is sent. Repeated alarms
with the same key inside the cooldown are suppressed only when wet mode is enabled. If severity
increases, it is sent immediately. When a ﬂood is identiﬁed (the same alarm happening again in the
cooldown period), a short check for alarm flood  warning is sent to the usual Slack channel and
to the shifters by email/sms. This warning is intentionally limited, so the ﬂood warning does not
become another ﬂood.
Integration Steps:  The new tester commands passed successfully, conﬁrming that the
secrets.txt  infrastructure works as expected. The new code also ran in dry mode, with ﬂood
decisions logged to the database but without actually suppressing email/SMS notiﬁcations. The
attached DB snapshot shows an example.
For the weekend, we will revert back to the good old trusted production version.
